# 研发工作核查

一个桌面端工具，用来核对**日报里申报的工作内容**和**当天在 GitLab 上的实际代码提交**是否一致。

解决的问题是：日报有工时、有项目、有描述，但这些文字和代码仓库里真实发生的事之间没有校验。这个工具把两边拉到一起，逐条给出判定，并指出两类问题：

- **日报写了但找不到对应提交** —— 描述可能夸大，或项目填错
- **有提交但日报没写** —— 漏报，跨项目协助、临时排查时很常见

## 工作原理

一次检查的流程：

```
选定日期 + 人员
      │
      ├─ 1. 取日报        →  HTTP 接口 / CSV 导入 / 演示数据
      │
      ├─ 2. 映射项目与人   →  日报里的「统一支付平台」→ gitlab:rd/payment-gateway
      │                      日报里的「张伟」→ gitlab 用户名 + 邮箱
      │
      ├─ 3. 拉取提交       →  按时间窗 + 作者过滤，逐条取文件变更
      │
      ├─ 4. 逐条判定       →  每条日报内容 + 该项目的候选提交 → 模型给出裁定
      │
      └─ 5. 汇总           →  按工时加权算符合度 + 反向找漏报提交 + 生成结论
```

### 判定档位

| 档位 | 含义 | 计入分数 |
| --- | --- | --- |
| 一致 | 提交内容明确支撑日报描述 | 满分 |
| 部分一致 | 方向对但范围/深度不够 | 半分 |
| 不一致 | 有该项目提交，但内容对不上 | 0 分 |
| 无提交 | 该项目当天没有提交 | 0 分 |
| 无法核对 | 项目未映射到仓库，或材料不足 | 不计入分母 |

### 分数怎么算

```
符合度 = 100 × Σ(工时 × 档位权重) / 可核对工时
```

两个关键取舍：

1. **非编码工作不进分母。** 开会、评审、写文档、答疑本来就不产生提交，把这些算成 0 分会让分数完全失去意义。工具会用关键词先判一轮，模型也会独立判断，两者任一命中即视为非编码工作。
2. **项目没映射上不进分母。** 这是配置问题不是员工问题，单独用「无法核对工时」呈现，避免因为没配好映射就给人打低分。

漏报的提交同样不进分数，单独列出来看——分数回答的是「日报里能自证的部分做得怎么样」，漏报回答的是「有没有该报没报的」。

### 提交归属时间窗

「某天的代码」不等于「当天 00:00–24:00 的提交」。默认窗口是 **前一天 20:00 到次日 08:00**（可配），覆盖晚上加班到凌晨和第二天早上补提交两种情况。

相邻两天的窗口会重叠，批量检查时同一个提交只归给**最早命中**的那天，所以「加班到凌晨」算在开始那天，和日报里「今天加班到几点」的写法一致。

## 快速开始

### 环境要求

- Node.js 20+ 与 pnpm
- Rust 1.90+（编译桌面端需要）
- Windows 需要 WebView2（Win11 自带）

### 安装与运行

```bash
pnpm install
```

桌面端开发（会启动 vite 并打开应用窗口）：

```bash
pnpm desktop:dev
```

只想调界面时，可以直接开浏览器跑，此时网络请求走 fetch、数据存 localStorage：

```bash
pnpm dev
```

打包安装包：

```bash
pnpm desktop:build
```

### 第一次使用

1. **设置 → GitLab**：填实例地址和 Personal Access Token，点「测试连接」。Token 需要 `read_api` 权限（只读，工具不做任何写操作）。连上后会自动发现仓库。
2. **设置 → 项目与成员**：
   - *项目映射*：把日报里写的项目名对应到 GitLab 仓库。页面上会列出「日报里出现过但还没映射的项目」，并且给出模糊匹配的猜测，点一下就能采纳。
   - *成员映射*：把日报系统里的人对应到 GitLab 用户名和邮箱。可以从已导入的日报里一键导入。
3. **设置 → 模型**：选协议（Anthropic 或 OpenAI 兼容）、填模型名和 Key，点「测试模型」。
4. **日报数据**：从内部系统同步或导入 CSV。
5. **执行检查**：选日期、勾人、开跑。

只想先看看效果，可以跳过 1、3、4 —— 日报来源默认为内置演示数据，不配模型也能跑（此时只判断「有没有提交」，不核对内容）。

### 样式分层

样式拆成三层，`src/styles/` 下三个文件各司其职：

| 文件 | 归属 | 内容 |
| --- | --- | --- |
| `index.css` | 手写 | 只做聚合，按 tailwind → theme 的顺序 `@import`，不写具体规则 |
| `tailwind.css` | **脚手架生成，禁止手工编辑** | 设计令牌（颜色、圆角）、`@theme inline` 映射、基础层 |
| `theme.css` | 手写 | 应用自己的主题覆盖与样式 |

`index.css` 里两个 import 的先后顺序有语义：同优先级下后加载者胜出，所以 `theme.css`
可以盖住脚手架给的默认值（例如把 `--font-sans` 从 Geist 换成系统字体栈）。

主题跟随系统深浅色。`tailwind.css` 和 `theme.css` 都写了 `.dark` 下的一整套变量，
切换逻辑在 `src/composables/theme.ts`，由 `main.ts` 在挂载前调用一次——
放在挂载前是为了避免深色系统下首屏闪一下浅色背景；不能用 `index.html` 里的内联脚本代替，
生产环境的 CSP 是 `script-src 'self'`，内联脚本会被拦掉。
需要「手动切换并记住选择」时，把 `theme.ts` 的 auto 逻辑改成读配置即可。

**`tailwind.css` 和 `src/components/ui/**` 禁止手工修改，只允许脚手架触发变更。**
这条规则的价值在于：任何时候都能用 CLI 重新生成而不用手工补救。目前这套分层下，
重新生成之后不需要做任何额外处理——`useMarkdownExtensions.ts` 的自定义和 Google Fonts
的处理都已经移走了（见下）。

### 数据存储

本地数据存在 SQLite 里（`src-tauri/src/db/`），文件在应用数据目录的 `task-inspector.db`。
用 `rusqlite` 的 `bundled` 特性自带 SQLite 源码，不依赖目标机器上的系统库。

表结构：

| 表 | 说明 |
| --- | --- |
| `settings` | 配置，整体存一行 JSON。配置项增删频繁，拆列会让每次加字段都要迁移 |
| `daily_reports` + `report_entries` | 日报。条目拆表是因为要按项目/按人跨日期检索，塞 JSON 里就只能全表扫出来在内存过滤 |
| `inspections` | 检查结果。摘要列（分数、工时、漏报数）单独成列供列表和统计查询，完整结果存 JSON 载荷 |
| `commits` | 提交缓存。留审计痕迹（结论引用了哪些提交事后可查），也是检索语料 |
| `projects` / `members` | 项目与人员实体，见「项目与人员」 |
| `meta` | schema 版本、迁移标记 |

迁移是**只追加**的：`MIGRATIONS` 里已发布的版本不能改，否则新老安装会出现不一致的 schema。

从旧版升级时有两步数据搬迁，都在首次启动自动完成、且幂等：
`store.rs` 把旧版「一条记录一个 JSON 文件」里的配置与检查历史搬进数据库（旧文件保留不删）；
`core/store/bootstrap.ts` 把旧版设置里的项目/人员**映射**搬成实体，搬完清空旧字段，
避免同一件事在两处各记一份。

### 检索：FTS5 + 向量混合

`search_hybrid` 把两路结果用 RRF（倒数排名融合）合成一个排序：

- **BM25（FTS5）** 负责字面命中：中文词组、代码标识符、文件名
- **向量**负责语义命中：换个说法描述同一件事也能召回

向量那一路是可选的——没配 embedding 服务、或索引还没建时自动退化成纯 BM25，
检索仍然可用，不会整个功能失效。

几个实现上的选择：

- **分词器用 `trigram`，不是默认的 `unicode61`。** 后者按空格/标点切词，中文整句会被当成一个词，
  等于搜不到。trigram 对任意三字符组合建索引，中文子串（「支付回调」）和驼峰标识符
  （`payCallback`）都能命中。代价是查询词至少 3 个字符，短查询在应用层退回 `LIKE`。
- **向量检索目前是在 Rust 里暴力算余弦**，没用 `sqlite-vec`（它还是 alpha）。
  万级数据下是毫秒级，且检索入口只有 `vec_top_k` 一个函数，
  等它出正式版或数据量涨到十万级以上再换进去，融合逻辑和表结构都不用动。
- **RRF 而不是加权求和**：BM25 分数和余弦相似度的量纲完全不同，
  加权求和要为每种组合调参，RRF 只看排名，不需要调。


### 仓库范围

**仓库范围按项目配置，没有全局过滤。**

- 每个业务项目在「项目」面板上关联**多个仓库**和**多个组**；组会扫描全部子组
- 点「解析关联仓库」展开成具体仓库并缓存，检查时直接用缓存，不必每次再调 GitLab
- GitLab 设置里只需要实例地址、Token 和「跳过 TLS 校验」这几项

另外还维护一份「仓库目录」：token 有权限的全部仓库（`/projects?membership=true`），
只用于「日报里的项目名对不上任何项目」时的模糊匹配候选。
大实例上仓库可能上万，所以有「仓库目录数量上限」（默认 2000）兜底，
触达上限会截断并在检查页明确提示。

**主要检查路径不依赖这份目录**：项目 → 关联的仓库/组是显式配置的，
所以目录不完整不会让已经配好的项目漏提交。

### 本地假 GitLab（开发自测）

没有真实实例时，可以用内置的假服务跑通整条链路——仓库发现的分页、
`membership=true` 的语义、提交时间窗、作者过滤、漏报判定，这些都只有在真拉一次数据时才能验证：

```bash
pnpm mock
```

它同时提供一个 OpenAI 兼容的假模型（返回写死的判定 JSON，走真实的 SSE 流式）。
启动后按提示把「设置 → GitLab」的实例地址和「设置 → 模型」的接口地址都指向 `http://localhost:9939`，
Token / API Key 填任意非空值即可。

假数据里有 5 个仓库，其中 2 个不在当前用户的成员范围内，用来验证「同步全部」不会越权拿到无关仓库；
提交里也特意留了一条没写进日报的，用来验证漏报判定。


### 脚手架与重新生成

项目按官方路径初始化：Vite 的 `vue-ts` 模板 + `tauri init`（Tauri 官方文档里的手动路径，
`create-tauri-app` 是一体化路径，产物结构一致），UI 层全部由 shadcn-vue CLI 生成：

```bash
# 基础组件
pnpm exec shadcn-vue add button card input label badge separator select checkbox \
  switch dialog tabs table textarea progress alert scroll-area tooltip avatar \
  skeleton dropdown-menu collapsible radio-group -y -o

# AI Elements（自定义注册表，不是基础组件）
pnpm exec shadcn-vue add @ai-elements/conversation @ai-elements/message \
  @ai-elements/loader @ai-elements/reasoning @ai-elements/sources -y -o
```

重新生成主题（会覆盖 `src/styles/tailwind.css`，不影响 `theme.css`）：

```bash
pnpm exec shadcn-vue init --force -y -d --template vite --src-dir
```

`components.json` 里 `tailwind.css` 指向 `src/styles/tailwind.css`，所以 CLI 会把生成结果
直接写进那一层，不会碰到另外两个文件。执行完 `init` 后确认 `components.json` 的
`registries` 里仍有 `@ai-elements`（`init` 有时会清空它）。

CLI 生成的 `tailwind.css` 里有一行在本工程不适用：Google Fonts 的 `@import url(...)`。
内网桌面应用不该往外发请求，生产 CSP 也会把它拦掉，结果是字体静默回退、更难排查。
这一行**不在磁盘上删**，而是在 `vite.config.ts` 的 `scaffoldCssShim` 插件里于构建期剥掉——
磁盘文件保持 CLI 原样，重新生成后无需手工补救。字体改在 `theme.css` 里用系统栈定义。

同文件里的 `@import "shadcn-vue/tailwind.css"` **必须保留**：它定义了生成组件依赖的
全部自定义变体（`data-open` / `data-checked` / `data-horizontal` / `shimmer` 等，共 79 处引用）。
误删的症状很隐蔽——构建照常通过，但 Tabs 会横向排版、Checkbox 失去选中态、
Dialog 没有进出场动画。改动 `scaffoldCssShim` 时留意这一点。

同理，markdown 的渲染扩展不再改 `src/components/ai-elements/message/useMarkdownExtensions.ts`
（那是生成物），需要定制时在应用侧包一层 `MarkdownProvider` 覆盖即可。

`src/lib/utils.ts` 也由 CLI 管（内容是 `export { cn } from "cn"`），
应用自己的工具函数放在 `src/lib/format.ts`，不要写进 `utils.ts`。

### 为什么网络请求走 Rust

有三个原因，都不是为了性能：

1. 内网 GitLab 不会返回 CORS 头，webview 里的 fetch 会被同源策略拦掉
2. Token 留在 Rust 侧就不会进入页面上下文，即使渲染出的内容有问题也拿不到凭据
3. 流式响应可以用 Tauri Channel 稳定地推给前端

前端通过 `src/core/bridge/` 这一层访问这些能力，接口不变，换实现不影响上层。

## 对接内部系统

### 日报接口

接口如果需要登录才能访问，在「设置 → 日报系统」里启用「接口登录」并填账号密码。
当前对接的这个内部系统的鉴权方式是：

```
POST {地址根}/login
Content-Type: application/x-www-form-urlencoded

loginInfo = Base64(用户名 + 验证码key + 密码)
key       = 验证码 key（没填时自动生成 UUID）
code      = 验证码（没填时自动补一个随机串）
type      = 0        ← 0 = 用户名密码，不校验图形验证码

→ { code: "200", data: { accessToken, userId, ... } }
后续请求带 X-Token: <accessToken>
```

几个实现上要注意的点：

- **`type` 配什么就发什么，工具不做任何推断或替换。** 内部系统里 `1` 是**需要图形验证码**的
  那条路径——它要的是人在页面上看出来的那四个字符，自动补的随机值永远过不了，所以自动化登录
  只能用 `0`。登录页的打包代码里那一行确实写着 `type: 1`，那是浏览器里的正常登录路径，
  和我们这条无头登录不是一回事，别照抄。

- **`key` / `code` 不能是空的。** 服务端即使不做校验也会读这两个字段，空值会直接报参数错——
  「服务器没用到」和「服务器可以没有」是两回事。用户名密码登录本来就不需要真验证码，
  所以没配就现场补一个（UUID / 随机串），每次登录换一组。
  **补出来的 key 和 `loginInfo` 里用的是同一个值**：服务端要靠 `key` 定位它在
  `loginInfo` 里的位置，两处不一致就会切错位置。
- **登录请求本身不是加密的，是 Base64。** 那个前端里确实有 AES-ECB（`CryptoJS`，key 是 hex 常量
  `313233343536373a`），但它只用于「记住密码」写 localStorage，登录接口用的是 Base64 拼接。
- **登录接口是那个前端里唯一不用 JSON 的接口**，其余都是 `application/json` + `X-Token`。
- **`code` 是字符串**（实测返回 `"401"`），不能直接和数字 200 比，否则连成功都会被判成失败。
- **Base64 里的 `+` 必须转义成 `%2B`**。表单编码里 `+` 代表空格，不转义的话服务端解不出 `loginInfo`。
  用 `URLSearchParams` 序列化即可。
- **登录失败的原因在 `data` 字段里**，且是个字符串（不是 `data.message`），
  比如 `{"code":"401","msg":"登录失败","data":"用户名或密码错误"}`。

#### 会话保持

token 有闲置失效时间，服务端的计时看的是「有没有请求」，所以想在失效前保住会话就得真的发请求。
`accessToken` 缓存在会话里跨多次检查复用，续期分三层，按可靠性从高到低：

| 配置 | 行为 |
| --- | --- |
| 填了探活接口路径 | 按频率打探活请求，会话不会断（首选） |
| 只填了空闲失效时间 | 没有请求时，在失效前重新登录一次 |
| 两个都填 | 以探活为主，失效前重登兜底 |
| 两个都留空 | 退化成被动重登：等请求被 401/403 打回再重登 |

探活频率留 0 时自动取「空闲失效时间 × 2/3」，留出的余量要能覆盖一次请求往返。
**注意这里不会默认成 0（不跑）**：填了探活接口却因为推不出频率而静默不执行，
是最难查的一类「配了没生效」。

设置页会实时显示会话状态（已登录 / 空闲剩余多少分钟 / 探活是否在跑 / 最近一次失败原因），
所以「到底有没有续上」不用靠猜。空闲失效时间的值需要问日报系统那边要，
在设置页填进去即可——不填也不会坏，只是每次过期要浪费一个 401 往返。

#### 拉取接口

当前对接的查询接口是 POST 分页式：

```
POST {地址根}/api/work/work-log/v2/page/send/me?page=1&limit=100
Content-Type: application/json
X-Token: <accessToken>

{"page":1,"limit":100,"queryContent":"","projectId":"",
 "startDate":"2026-10-16 00:00:00","endDate":"2026-10-16 23:59:59",
 "createUserIds":[],"logSendUserRead":""}
```

路径、请求方法、**整份请求体**都在设置页可改，因为各家的字段名不统一。
拉的是**别人发给 / 抄送给你**的日报；不要配成 `page/self`——那是自己的日志，
既不是核查对象，也会让检查结果只剩本人。
内网用自签证书时，还要打开同一页上的「跳过 TLS 证书校验」——
**这一项只在桌面端有效**，浏览器里绕不过去（原因见文末「排查」）。
模板里可用的占位：

| 占位 | 值 |
| --- | --- |
| `{date}` | `2026-10-16` |
| `{startDate}` / `{endDate}` | 同 `{date}`（一次只查一天） |
| `{startDateTime}` / `{endDateTime}` | `2026-10-16 00:00:00` / `2026-10-16 23:59:59` |
| `{page}` / `{limit}` | 当前页 / 每页条数 |

占位分两种写法：整体带引号的 `"{page}"` 替换成**数字**，写在字符串内部的 `{date}` 原样拼接。
上面的请求体靠这一点同时保住 `"page":1` 是数字、`"startDate":"..."` 是字符串——
内部系统对这两者的类型是敏感的，全当字符串传会被判成参数错误。

**日期这一处踩过一次坑，值得记下来。** 这个系统的起止日期是**日期时间**类型，
传纯日期 `"2026-10-16"` 会在反序列化那步直接抛异常，而服务端的全局异常处理器
把它兜成一句「请求体读取异常」——字面上指向请求体，实际原因是日期格式，
照着那句话排查会一直往错的方向走。所以这里用 `{startDateTime}` / `{endDateTime}`。
判断依据不是猜的：抓前端真实请求时，它发的就是 `"2026-10-14 00:00:00"` 到
`"2026-10-16 23:59:59"`。

以后换系统遇到类似的、指向含糊的服务端报错，最快的办法就是**抓一条前端自己的请求做对照**——
我们发出去的东西现在会完整记进日志（请求头名字、content-type 的值、请求体原文），
两边一比就知道差在哪。

三个约束都是为了让这个接口不被我们打满：

- 翻页**串行**，同一批里两次请求之间至少隔 300ms（批量载入日期范围时最容易连发）
- 翻到**空页**就停，或者整页都是已见过的数据（接口忽略了 `page`）也停。
  这个系统的最后一页长这样：`{"page":2,"limit":100,"count":"2","data":null}`——
  `count` 仍说总数是 2，但 `data` 直接给 `null`。空页要和「字段映射配错」区分开：
  配错时取到的是个**对象**（比如 `itemsPath` 写成 `data`），那才报错；
  取到 `null` 只说明翻到底了
- 「最多翻页数」兜底，接口始终返回满页时不会无限拉下去

翻到底会多出一个「确认没有下一页」的请求（N 页数据就是 N+1 个请求）。这是刻意的：
靠「这一页不满」来判断结束会快一次请求，但服务端把 `limit` 卡小时会静默漏数据，
比起慢一点，漏数据难发现得多。

字段映射在设置页都可改，换一套内部系统不用动代码。用点号路径指向响应 JSON，这个系统返回的是：

```json
{
  "code": 200,
  "data": {
    "page": 1,
    "limit": 10,
    "count": "906",
    "data": [
      {
        "workDate": "2026-10-15 00:00:00",
        "workContent": "提取后端主干代码…\n切换所有模块为生产环境配置",
        "createUser": "245950518022297",
        "createUserName": "孟泽林",
        "projects": [
          {
            "projectId": "245849054994440",
            "projectName": "平战结合管理平台项目",
            "projectNumber": "DF-XM2021-405",
            "workDayPercent": 100
          }
        ]
      }
    ]
  }
}
```

对应填：

| 字段 | 值 |
| --- | --- |
| 日报数组 | `data.data` |
| 日期 | `workDate` |
| 成员 ID | `createUser` |
| 成员姓名 | `createUserName` |
| 条目数组 | `projects` |
| 项目名 | `projectName` |
| 项目编码 | `projectNumber` |
| 工时 | `workDayPercent` |
| 工作内容 | `workContent` |

有两处结构上的错位，是这个系统特有的，映射时要注意：

- **工作内容在日志级，不在条目级。** 一条日志只写一份工作内容，`projects[]` 里只有项目和占比。
  所以「工作内容」在条目里取不到时会**退回日志级再取一次**——这样一天写多个项目时，
  同一份内容会挂到每个项目上，判定时各项目各自拿它对照自己的提交。
- **工时是占比不是小时。** `workDayPercent: 100` 表示占当天工时 100%。权重本身按比例算，
  直接当小时用不影响打分，但界面上会显示成「100 小时」。所以下面有个「100% 折算为 __ 小时」
  （默认 8），按八小时制换算，比例一分不差。填 0 表示不折算。

选好日期点「拉取这一天的日报试试」，会把解析出的第一条打印出来对照——成员、项目、工时、内容四项都摆在一行，
配错哪一项一眼就能看出来。**日期默认是昨天**：日报当天晚上才上报，白天查今天永远是空的，
拿它当「接口通不通」的判据会一直得出错误结论。数组藏得比较深时也不用自己翻响应：取到的不是数组的话，
报错里会直接列出「响应里这些位置是数组」。

## 项目与人员

项目和人员是**一等实体**，有自己的面板（左侧「项目」「人员」），不再只是设置里的一组映射规则。

这么做是因为日报里本来就带 `projectCode`，说明「项目」在两端都被引用，应该有身份和生命周期；
而「日报里的叫法 → GitLab 仓库」这种映射，本质上就是项目自己的名称/编码/别名，不必分成两处维护。

### 项目

**项目以日志中心为准。** 「从日志中心同步」按日志中心的项目清单建本地项目；
GitLab 只是它的代码来源，不再按仓库生成项目（早期版本是那样做的，旧数据会自动迁移成
「单仓库关联」，不会丢配置）。

字段分两类：

**业务身份**（来自日志中心，也可以手填）

| 字段 | 说明 |
| --- | --- |
| 项目名称 | 必填；来自日志中心的项目，名称会跟着日志中心更新 |
| 项目编码 | 对应日报的 `projectNumber`，填了优先按它匹配 |
| 别名 | 日报里同一个项目的其它叫法，避免每换种写法就新建一个 |
| 匹配方式 | 完全相同 / 包含 / 正则 |
| 参与检查 / 关注 | 停用后不参与匹配；关注决定它是否进入检查范围 |

**GitLab 关联**（一个项目可以关联多个）

关联项分两种：

- **仓库**：指向一个具体仓库，例如 `group/repo`
- **组**：指向一个组，解析时**扫描该组下的全部子组**

在项目编辑表单点「搜索并添加仓库/组」，会打开 GitLab 选择器：默认用**项目编码**作为关键词
（没有编码时用项目名称），**一个输入同时模糊匹配仓库名、组名和完整路径**；结果里用徽标区分
仓库和组，只显示当前 Token 能看到的资源，已添加的会标记出来。找不到时仍可在选择器底部手动填写路径。

点「解析关联仓库」会把关联展开成具体仓库并缓存下来——检查时直接用展开结果，
不必每次再调 GitLab。组里新增的仓库要重新解析才会出现。

几个行为：

- **前提是所有项目的代码是分开的**：一个仓库只属于一个业务项目。如果两条项目关联到同一个仓库，
  同一批提交会被两个项目各算一遍，分数会失真
- 解析失败会精确到某一条关联（哪个仓库/哪个组），失败的那部分提交会被漏掉，
  所以不能静默略过
- 还没解析出仓库的项目，它的日报条目会判成「无法核对」——这是配置问题，不是员工的问题

还有两个派生指标：

- **同步状态**：已解析 / 解析失败 / 未解析 / GitLab 上已找不到
- **引用次数**：该项目在已载入的日报里被提到过多少次，走检查引擎的同一套匹配规则

### 人员

**日报侧**：姓名、日报成员 ID、工号、团队、岗位。
**Git 侧**：用户名（**可以有多个**）、GitLab 用户 ID、邮箱（也可以多个）。

一个人为什么需要多个用户名？因为 Git 里同一个人经常是「好几个人」：换过账号、
本机 git config 没配、用中文名提交、用私人邮箱。只认一个身份必然漏提交，
而**漏提交会被判成「日报写了但代码没有」**，方向正好反了。
所以检查时不传 GitLab 的 `author` 过滤（那个只能给一个值），
而是把时间窗内的提交拉回来，在客户端按「用户名 + 邮箱」的完整列表筛。

这也是为什么同步完人员之后，**只要 Git 用户名对不上就一条提交都匹配不到**——
显示出来的现象是「这个人当天没提交」，实际原因是身份没配。

#### 从日志中心同步人员

「人员」面板的「从日志中心同步」以日志中心的用户清单为准建人：

- 读「设置 → 日报系统 → 用户清单」里配的接口（默认
  `GET /api/system/user/queryList?deptId=&permission=0&userType=1`）
- 按「**日报 ID → 工号（登录名）→ 姓名**」匹配本地人员。
  姓名只在唯一命中时才用——重名会列出来让人裁决，猜错会把两个人的结论算到一起
- 补上 `reportMemberId`（这项最关键）、工号、部门、邮箱，
  以及用登录名给 Git 用户名起个头
- **只补空着的字段**，已有值不覆盖

`reportMemberId` 为什么关键：日志系统的日报用它的用户 ID 标识作者，
而 LDAP 建的人这个字段是空的。对不上时，同一个人会在检查页出现两次——
一条有 GitLab 身份但没日报，一条有日报但没身份，结论直接失真。

**关于密码：** 那个用户清单接口会把 `loginPwd` 一起返回（这是接口设计的问题）。
我们只按配置的字段映射读取 ID / 姓名 / 登录名 / 部门 / 邮箱五项，
**密码不进入任何数据结构，不落库、不进日志**。日志里对含有 `loginPwd` 的响应正文
也做了屏蔽。

#### 从 LDAP 同步人员

LDAP 现在退成**补充来源**：它仍然能补邮箱和组织架构，但不再决定「有哪些人」。
同步的匹配键仍然是「工号 → 登录名 → 姓名」，邮箱按来源分别记账。

派生指标里有两个是配置问题的探测器：

- **缺 GitLab 身份**：判定时无法按作者过滤，结果会混进别人的提交
- **邮箱冲突**：同一个邮箱被多个成员声明。这时「这条提交是谁的」判断不了，
  双方都会算成自己的，结论直接失真——属于必须人工裁决的冲突

「从 LDAP 同步」是主要的人员来源方式，见下节。

### 关注

项目和人员各有一个关注开关，默认全部关注。它是用户圈定「我关心哪些」的方式，三处生效：

1. **面板列表**默认只显示关注的（搜索时不受此限制——搜一个明确的名字却因为没关注而搜不到，
   比搜出多余结果更让人困惑）
2. **检查页默认只勾选关注的人**。未关注的人仍然列在名单里（带「未关注」标记），
   可以手动勾上——所以它是「默认选中」而不是「不许检查」
3. **未关注的项目不参与匹配**。它的日报条目算「无法核对」，说明里会写明
   「项目「X」没有关注，本次不检查它」，这条工时也不计入符合度的分母

第 3 条是**硬过滤**，和前两条性质不同：取消关注某个项目会直接改变结论的口径——
那天在该项目上的工时会从分母里去掉，剩下项目的表现占比因此变大。
所以「因为我眼下不关心」用关注，「因为它不该被考核」用停用（`enabled`）。

两者的区别可以这样记：**停用是「别用这个配置」，关注是「我眼下关不关心」。**
停用的人不进检查页名单，未关注的人还在名单里、只是不默认勾选。

### 批量操作

「项目」和「人员」两个面板都支持多选：表头勾选框全选**当前列表**（受搜索和筛选影响），
勾上之后上方会出现操作栏。

- **关注 / 取消关注**：批量改关注状态
- **删除**：弹确认框，删掉的是配置本身（名称、编码、别名、GitLab 关联），不可撤销

「关注」和「删除」的区别值得说清楚：**取消关注只是把它移出视野和检查范围，配置还在**；
删除才是把配置本身扔掉。想让它消失一阵子，用取消关注。

### 从日志中心同步项目

日志中心里「项目」是独立的业务实体、自带编号（`projectNumber`，如 `DF-XM2021-405`）。
「项目」面板的「从日志系统同步」按它建项目：

- 读「设置 → 日报系统 → 项目清单」里配的接口（默认 `GET /api/work/work-project/list/simple`），
  和拉日报共用同一套地址、鉴权和证书设置
- 认项目的顺序：**日志中心 ID → 项目编号 → 项目名称**，两边都去空白、忽略大小写
- 来自日志中心的项目，名称和编码会跟着日志中心更新；手工建的项目只补空，不覆盖
- 弹窗会先算清楚「远程 N 个 / 本地能对上 M 个 / 本地没有 J 个」，确认后才写库

同步只建项目和业务身份，**不会自动关联仓库**——日志中心不知道哪个业务项目对应哪些代码仓库，
关联要单独配（见上一节）。

**编码匹配优先于名称**：日报条目带编码、项目也填了编码时直接命中，不看名字。
这比按名称匹配稳得多——名字会被改写、会带后缀、会有人用别名。

### LDAP（本版本暂未接入）

人员以**日志中心**为准（见上一节），LDAP 的界面入口已经从这一版移除。
Rust 侧的实现（`src-tauri/src/ldap.rs`）和配置项都还在，以后要接回来不用重做。
下面保留原来的说明，供接回时参考。

人员以目录服务为主数据源，在「设置 → LDAP」配置后，到「人员」面板点一次同步即可批量建好。

连接由 Rust 发起（LDAP 是二进制协议，浏览器连不了），服务账号密码不进 webview。

配置项：服务地址（`ldap://` / `ldaps://`）、Base DN、绑定账号与密码、过滤器、
单页条数、超时、跳过证书校验，以及**属性映射**——
AD 和 OpenLDAP 的属性名差别很大（`sAMAccountName` vs `uid`，`displayName` vs `cn`），
所以登录名/姓名/邮箱/工号/部门/岗位各对应哪个属性都要能改。

默认过滤器排除已停用的 AD 账号（`userAccountControl` 的 ACCOUNTDISABLE 位）；
OpenLDAP 没有这个属性，需要改成比如 `(objectClass=inetOrgPerson)`。

同步的三条规则：

1. **按「工号 → 登录名 → 姓名」认人**。工号最稳定（改名、换账号都不影响），
   姓名最容易撞车只能兜底。
2. **不覆盖日报成员 ID**。那个字段来自日报系统，LDAP 里没有。
3. **邮箱是合并而不是替换**。本地可能手工维护过别名邮箱。

**同步不会删除人**：目录里没有的人不会被自动删掉。离职后账号被禁用是常态，
但历史检查记录还要能看。需要停用请到「人员」面板手动改。

### 属性映射的排查

AD 和 OpenLDAP 的属性名差别很大，靠猜会得到「同步成功但一个人都没建出来」这种结果，
而且报错完全没有指向性。所以「设置 → LDAP」里有**诊断属性映射**：
它搜一批真实条目，统计目录里到底有哪些属性，列出当前每个映射的命中数，
并对取不到值的字段给出可一键采纳的替代建议。

命令行版本（排查真实目录时迭代更快）：

```bash
cd src-tauri
cargo run --example ldap_probe -- <配置文件.json>
```

配置文件就是那份 LDAP 设置的 JSON。**里面含密码，别提交到仓库、也别外发输出。**

诊断会把 `userPassword`、`sambaNTPassword`、`krbPrincipalkey` 这类敏感属性的值隐去——
用 `*` 请求属性时，只要目录 ACL 没挡住，口令散列也会一起返回。
工具不需要这些值，但会报告「目录返回了它们」，因为这通常说明目录侧的 ACL 过宽，值得找运维确认。

另外两处容错：

- **过滤器缺最外层括号会自动补**（`objectClass=person` → `(objectClass=person)`）。
  LDAP 过滤器必定以 `(` 开头，补上永远是对的，不值得让人为此挨一次报错。
- **绑定账号与搜索起点填反会被识别出来**。`ou=` / `dc=` 开头的是容器，不可能是有密码的账号；
  这类手误默认只报「凭据无效」，完全不指向真正原因。

## 活动视图

「执行检查」的视角是「一天 × 一个人」，由日报驱动。另有两个视角，从代码这边看。

两个视图里的提交都可以**点开看内容**：弹窗展示提交信息正文、改动文件清单和 diff 正文。
diff 是点开时单独拉一次的（`commits/:sha/diff`），不在扫描阶段预先取——一次扫描几十条提交
各拉一次 diff，请求数和耗时都会翻好几倍，而绝大多数提交只是扫一眼标题就够了。

### 项目活动

选一个项目 + 一段时间（默认昨天），列出这段时间里**谁在该项目提交了什么**、**谁在日报里报了什么**。

项目选择器**支持搜索**（名称、编码、仓库路径都能搜）——项目一多下拉列表就没法用了。

- 提交按「前一天 20:00 ~ 次日 08:00」归到日期，和「执行检查」是同一套规则，
  所以同一个提交在两个页面归属的日子一致
- 行按「日期 × 人员」排，「有提交、日报没写」和「报了工时、当天没提交」分别标出来
- 只扫「关注且启用」的项目——未关注的项目不参与检查，这里也不看

提交是逐个仓库串行拉的，所以项目多的时候会慢。关注范围超过 60 个会先提醒，超过 120 个直接拦住。

### 人员活动

选一个人 + 一天（默认昨天），把当天在**各项目**上的几件事并排看：

| 列 | 含义 |
| --- | --- |
| 提交 | 当天在该项目下的提交条数与明细（可点开看 diff） |
| 代码量 | 当天在该项目下的增删行数 |
| 申报工时 / 申报占比 | 日报里的工时，以及它占当天申报总工时的比例 |
| 估算占比 | 模型**只看提交**估出来的产出占比 |
| 偏离 | 申报占比 − 估算占比，超过 15 个百分点才标色 |

四个刻意的设计：

1. **估的是相对占比，不是小时数。** 同样 100 行代码，新手要一天、熟手要一小时，
   估绝对工时估的是个人效率；而「这天 70% 的产出在 A 项目」是可比的，
   也正好能和申报占比直接对照。
2. **估算过程看不到日报。** 一旦把申报的占比喂给模型，它会顺着那个数字复述，
   对照出来的偏离就全是假的。输入只有提交。
3. **提交少于 3 条就不给估算**，只显示「样本不足」。三条提交以下任何占比都是噪声，
   而这个数字可能被拿去和人对话——一个没有依据的 0.8 比没有数字伤害更大。
4. **改动行数不等于投入时间。** 排查一个线上问题、最后定位到一行配置改掉，可能耗掉两小时；
   而加一个常规页面可能只花一小时。所以估算会读提交正文里描述的排查过程，
   遇到「排查 / 定位 / 复现 / 根因 / 线上问题」这类字样时按**问题复杂度**估，
   而不是按改动量估——否则一个查了两小时的问题会被算成几乎没干活。

估算只覆盖「有提交的项目」，所以「报了工时但当天没提交」的项目估算占比一列是「—」，
这本身就是信号，不要读成「估算为 0」。

## 项目对话与代码工具

项目列表和项目画像页可以进入「项目对话」。回答会先读取项目画像、最近 30 天提交和
相关日报；如果本机装了 codegraph / graphify，还会先规划代码工具调用，把符号、调用关系
和模块细节带进回答。工具调用会显示在回答上方，可展开看参数和原始结果。

- **codegraph**：需要项目目录已有 `.codegraph/` 索引。在项目目录运行
  `codegraph init -y`；索引是用户决定，应用不会自动建。- **graphify**：需要 `graphify-out/graph.json`。先运行
  `graphify update <项目目录>`，应用会用该目录启动 `graphify-mcp`。
  多仓库项目可以在「设置 → 代码分析 → MCP 服务器」里用 `--graph` 指定图文件。
- 应用会自动从 PATH / 设置里发现 codegraph / graphify，也可以添加其他 stdio MCP 服务。
- 工具结果会截断后发送给模型；项目资料和工具结果都会发到「设置 → 模型」里配置的服务。
- 没有索引时工具会明确报错，模型不会用编造的符号或调用关系补答案。

## 应用助手、官方文档与内置工具

侧边栏的「应用助手」是应用级对话，不绑定具体项目；项目对话里也有同一套内置工具。
官方文档随应用版本下发（`src/core/knowledge/docs/*.md`，通过 `?raw` 打进前端包），
用户不需要自己配置 skill 或 MCP。

- **`docs.search`**：检索官方文档。功能、设置、数据口径、报错类问题先查文档，不凭印象回答。
- **`members.list` / `members.ensure`**：查询人员；按「日报 ID → 工号 → 唯一姓名」幂等地新建或补齐邮箱、GitLab 用户名。只补空字段，不覆盖、不删除、不合并冲突账号。
- **`members.scanProjectAuthors`**：扫描项目**全部已解析的 GitLab 仓库**，汇总提交邮箱、姓名、提交数，并和现有成员匹配，输出「已绑定 / 建议绑定 / 未匹配」。问「这个项目有哪些开发、账号邮箱是什么」时用它，而不是只看一个仓库。
- **`members.ensureMany`**：一次为多个成员补齐邮箱/用户名，整批只弹一次确认；任何一项冲突则整批不写。
- **`members.bindProjectAuthors`**：重新扫描项目全部仓库、匹配现有成员并准备绑定，扫描和绑定准备一次完成，只弹一张确认；用户说「采纳 / 绑定吧 / 继续」时直接用它。
- **`projects.list` / `projects.ensure`**：查询项目；按编码 → 名称 → 别名匹配，校验 GitLab 仓库/组是否存在，已存在则忽略，新增后重新解析仓库。不会在 GitLab 侧创建组、仓库或用户。
- 对话按 **agent harness** 方式运行：模型可以反复「查询 → 看结果 → 继续」，直到自己认为完成；没有固定轮数或固定工具次数。单次回答有 100 次调用 / 15 分钟的安全预算（防止跑飞），达到后会暂停并提示回复「继续」。所有写操作和命令仍然逐条确认。
- 所有写操作都会在对话里出现确认卡片，显示将要新建/修改的字段；用户允许后才写 SQLite。
- 内置技能由能力清单和工具注册表自动拼装，新增工具不需要再维护一份用户文档或 skill 文件。

## 本地代码画像

项目画像不强制要求先解析 GitLab 仓库。画像页的「扫描范围」可以直接添加本机代码目录，
应用会扫描这些目录生成模块结构和报告；目录记在画像里，下次生成自动回填。

**分支：** 自动克隆会保留 origin 的全部远程分支和标签（仍可按设置做浅克隆）。画像会先比较
各分支最近提交时间，**优先分析最近提交的分支**；如果本地 checkout 不在目标分支，应用会在临时
`git worktree` 里分析目标分支，不改动用户工作区，并记录「本地当前分支 / 画像分析分支 / 分支引用数量」。
项目对话可以用 `projects.branches` 先确认每个仓库的分支再回答代码类问题。

- 没有 GitLab 关联时：画像、代码结构、项目对话里的本地命令仍然可用；提交记录为空。
- 需要核对提交、执行检查时：仍要给项目关联 GitLab 仓库（或后续接本地 git 提交扫描）。
- 本地目录会先扫描一次，空目录不会加入。

## 命令执行与人工确认

「设置 → 代码分析 → 命令执行」可以允许项目对话提议本机命令，默认关闭。
打开后仍然**每条命令都要确认**：

- 只对桌面端、且项目画像里有本地仓库目录的项目生效；cwd 必须是这些目录之一
- 确认卡片显示完整命令、工作目录、目的、超时；高风险模式（`rm -rf`、`git reset --hard` 等）标红但不自动拦截
- 确认卡片支持「本次回答内全部允许」：点一次后，这次回答后续的成员/项目写操作不再逐条弹卡片；如果是命令卡片，后续命令也一起放行。新提问会恢复逐条确认
- 命令以当前用户权限执行，**没有沙箱**；cwd 只决定起始目录，命令仍可 `cd` 或访问绝对路径
- 默认 60 秒超时（可调 5–300 秒），超时或取消会杀掉进程树；输出上限 100k 字符
- 页面刷新时等待中的确认会失效并明确提示「操作未执行」，不会留下可点击的死卡片

## 数据与隐私

- 所有数据都在本机：配置、日报、检查历史、提交缓存统一存在应用数据目录的
  `task-inspector.db`（SQLite，见「数据存储」）。不经过任何服务器
- 工具对 GitLab 只做读操作
- 「设置 → 数据」里的配置导出**包含 Token**，外发前请先删除
- 同一页有「重置数据」：只清业务数据（日报、检查历史、提交、项目、人员，配置保留），
  或者全部重置（连 GitLab / 日报 / 模型配置一起清，等于重新装一遍）。清空不可撤销

## 发布

GitHub Actions 工作流在 `.github/workflows/release.yml`，也可以手动触发（workflow_dispatch）。

| 触发 | Release | 说明 |
| --- | --- | --- |
| push `main` | tag `latest`，名称 **Latest** | 滚动发布，每次覆盖同一份 release 的安装包；`latest` 标签会移到最新提交 |
| push tag `v1.0.0` | tag `v1.0.0`，名称 **1.0.0** | 版本发布；构建时把 Tauri 版本覆盖成 `1.0.0` |

每个平台会产出安装版和免安装版：

- **Windows**：NSIS `*-setup.exe`、MSI `*.msi`、`*_windows_x64_portable.zip`（解压后直接运行，需要系统已安装 WebView2）
- **macOS**：通用 DMG（Intel 与 Apple Silicon 通用）、`*_macos_universal_portable.zip`（解压后把 `.app` 拖进「应用程序」）

注意事项：

- macOS 产物**未签名、未公证**。首次打开请右键 →「打开」；如果仍被拦截，
  执行 `xattr -dr com.apple.quarantine /Applications/TaskInspector.app`
- 版本号来自 tag（`v1.0.0` → `1.0.0`）；main 构建沿用 `package.json` 的版本
- 工作流会先跑 `pnpm typecheck`，再用 `tauri build` 构建对应目标
- 正式分发需要签名时，在仓库 Secrets 里配置 Apple / Windows 证书，并在工作流里补上签名步骤

### 应用内自动更新

安装版会在启动几秒后检查更新，页头右上角也可以手动检查。更新包必须带 Tauri 签名；签名对不上不会安装。

- 更新源：`https://github.com/swaince/task_inspector/releases/latest/download/latest.json`
- 构建时用 `TAURI_SIGNING_PRIVATE_KEY` 给 updater 产物签名。私钥在本机
  `~/.tauri/task-inspector.key`，同时存放在仓库 Secrets，**不要提交到仓库**
- 发布作业会为 Windows 的 `.nsis.zip`、macOS 的 `.app.tar.gz` 生成 `.sig`，
  并生成 `latest.json`；这些文件和安装包一起挂在 Release 上
- 只有版本 tag 的 Release 会标记为 GitHub Latest；main 的滚动 Release 仍然发布，
  但不作为自动更新通道，避免每次推 main 都触发客户端升级
- 自动更新只覆盖 **NSIS 安装版**和放到 `/Applications` 的 macOS `.app`；
  免安装 zip、MSI 安装版不保证能自更新
- **免安装版仍然可以更新**：应用内检查到新版本后，更新弹窗里有「打开最新 Release」入口；
  关闭应用，用新 zip 里的 exe 覆盖旧文件即可。项目、检查历史和配置在 AppData 里，不受影响
- 第一次带自动更新的版本需要用户手动安装；从下一个版本开始才能在应用内升级
- 私钥丢失后，已发布的旧客户端无法验证新更新，只能让用户手动安装新版本；
  请把 `~/.tauri/task-inspector.key` 备份到安全位置（本密钥没有设置密码）

本地 `pnpm desktop:build` 不需要签名私钥：`createUpdaterArtifacts` 只在 CI 的配置覆盖里开启。

## 尚未接完的部分

- **检索还没有界面入口。** `search_hybrid` 命令和 FTS5 索引已经可用（有测试覆盖），
  但界面上还没做搜索框，提交缓存也只在每次检查时顺带写入
- **向量那一路还没有生成流程。** `embeddings` 表和 `search_hybrid` 的向量参数都就绪，
  但还没有「把提交/日报条目批量送去 embedding 接口并入库」的流水线，
  所以现在实际跑的只有 BM25 那一路
- **提交缓存只写不读。** 每次检查仍然完整向 GitLab 拉取，缓存目前只用于留痕和检索语料。
  后续可以按「时间窗 + 项目 + fetched_at 新鲜度」做读缓存，重复检查同一天时省掉一轮请求
- **LDAP 已对真实目录验证，但只覆盖了一种目录。** 连接、分页搜索、属性映射和对账逻辑
  都跑通过（对真实 OpenLDAP 连续多次同步：91 条全部入库、0 条跳过），
  但 AD 的属性名和过滤器与 OpenLDAP 差别很大，换目录仍需先用「诊断属性映射」核一遍
- **日报登录只验证到「拿得到 token」。** 登录请求的地址、参数拼接和编码都对着一份
  真实的 401 响应核过，但登录后的列表接口路径和字段映射要用真实账号配完才算数；
  会话保持的三个续期层同理——空闲失效时间只有问日报系统那边才能拿到，
  拿到之前跑的是「被动重登」那一层
- **项目面板的同步依赖「设置 → GitLab」的发现范围。** group 留空时同步全部有权限的仓库，
  大实例上首次同步会翻很多页
- **一个项目对应一个仓库。** 旧模型里一条映射可以指向多个仓库，迁移时只取了第一个，
  其余需要在项目面板里另建项目

## 已知边界

- 只检查代码提交这一种产出。设计稿、测试报告、线上运维操作等无法从 GitLab 验证
- 描述笼统（「日常开发」「推进项目」）时有实质提交就倾向判为一致，不做过度解读
- 提交信息质量差（全是「fix bug」）时判定准确度会下降，工具会在理由里说明依据
- 模糊匹配项目名故意保守，宁可报「需要人工确认」也不猜，猜错会让结论失真

## 排查

**打包后打开是白屏。**
先看是不是 CSP 拦了资源。生产环境的 CSP 在 `src-tauri/tauri.conf.json` 的
`app.security.csp` 里，配得比较严（默认只允许加载本地资源，网络请求全部走 Rust）。
如果某个依赖需要额外权限，把它加进对应的指令即可；临时验证可以先把 `csp` 改成
`null`，确认是 CSP 问题之后再逐步收紧。

**`pnpm desktop:dev` 报端口被占用。**
vite 配置成 `strictPort: true`，1420 被占用时会直接失败而不是换端口，这是刻意的——
Tauri 的 `devUrl` 写死了 1420，静默换端口会导致窗口打开后连不上开发服务器。

**检查结果里大量「项目未映射」。**
到「项目」面板看顶部那张「从未被日报引用」的统计卡，它列出的就是匹配键和日报里的写法
对不上的项目；项目的名称 / 编码 / 别名和匹配方式都在那里改。

**「测试登录」失败，但提示说不清楚原因。**
先看错在哪一层，两者处置方式完全不同：

- **提示里带着 HTTP 状态码**（404 / 405 / 415）——请求已经发出去了，服务端回了话，
  照提示改地址、方法或请求体编码即可。
- **提示是「请求没发出去」**——根本没连上，一个字节都没出去。

后一种最常见的两个原因：

- **内网自签证书。** 浏览器模式（`pnpm dev`）**绕不过证书校验**——那走的是页面的
  `fetch`，证书校验由浏览器自己做，页面上没有任何开关能跳过。要么先在浏览器里直接打开
  那个地址、手动信任证书，要么改用桌面端并在「设置 → 日报系统」打开
  「跳过 TLS 证书校验」。桌面端那条链路走 Rust，能真正跳过校验。
  GitLab 和 LDAP 各自也有同样的开关。
- **服务端没返回 CORS 头。** 同样只能在桌面端解决，请求由 Rust 发出，不受同源策略约束。

这两种在浏览器里都被压成一句 `fetch failed`，所以界面会把可能性列出来——
它们没法从 JS 侧区分。
