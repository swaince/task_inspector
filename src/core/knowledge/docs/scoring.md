# 工时与得分口径

应用里出现三类「工时/分数」，含义完全不同，不要混着读。

## 1. 日报申报工时

来自日报系统的 `workDayPercent` 或工时字段。它表示**申报**，不是实际产出：

- 一天多个项目时，各项目的申报工时相加；
- 申报 8h 不代表写了 8h 代码，也可能是会议、评审、答疑；
- 检查的加权分母用的是申报工时。

## 2. 有效工时（证据推算）

有效工时不是一个精确值，而是由可观测证据推算出来的**区间**：

- **下限（代码可核对）**：只认提交。按提交会话估算，会话之间有首尾缓冲，再乘一个保守系数；
- **上限**：叠加 MR / 评审 / Issue 活动、当天首末活动的在岗跨度，以及可选的模型任务估算；
- 同一份工作可能在提交、活动事件、在岗跨度里重复出现，所以取最宽的一路，**不相加**；
- 参数在「设置 → 分析 → 工时估算口径」里按公司情况标定（会话间隔、首尾缓冲、单日上限、有活动日下限、在岗折算比例等）。

两种边界：

- 只有提交、没有其它活动时，下限和上限都可能只有 1–2h——这反映的是「系统能看到的工作」，不是全天工作投入；
- 会议、答疑、写方案这类没有系统痕迹的工作不会被强行计入，也不会因为申报写了 8h 就把结果抬到 8h。

工作饱和度 = 有效工时中值 / 标准工时。它适合看本人趋势和团队分布，**不适合跨人排名**，也不适合当考勤。

「模型任务估算」是一个可开关的补充信号：把提交、活动证据和日报内容一起交给模型，估算每日投入区间。日报在这里是**待核实的声明**，用来识别没有代码痕迹的工作类型，不会直接抄成工时。

## 3. 符合度（0–100）

检查结果里的加权分数，按日报工时加权：

- 一致 = 100；
- 部分一致 = 60（以判定规则里的权重为准）；
- 不一致 = 0；
- 无提交、无法核对 = 不进分母。

所以「100%」只表示**有可核对内容的条目全部一致**，不表示当天产出 8h，也不表示日报写得完整。如果所有条目都无法核对，分数显示「—」。

## 覆盖率

覆盖率描述「有提交、有日报、能互相印证」的比例，用来判断结论的可靠程度，不直接参与得分。

- 覆盖率低：先查人员身份、项目关联、GitLab 权限；
- 覆盖率正常但符合度低：再逐条看判定理由；
- 未引用提交多：可能是日报描述太笼统，也可能是另一个项目的工作。

## 常见误读

| 现象 | 不代表 |
|---|---|
| 100% | 日报完整、产出等于申报工时 |
| 0 分 | 员工没干活；先看分母是否为 0 |
| 「—」 | 不合格；通常是没有可核对内容 |
| 有效工时低于申报工时 | 一定在摸鱼；非编码工作本来就不计入，先看上限与活动证据 |
| 有效工时只有 1–2h | 一定没干活；可能只是提交少、评审和会议没有系统痕迹 |
| 未引用提交多 | 整个项目漏报；可能只是证据没引用到 |
