# 执行检查

「执行检查」按「日期 × 关注成员」批量运行，检查范围由**关注且启用的人员**和**关注的项目**共同决定，不再手选检查对象。

## 参数

- **起始/结束日期**：一次最多 60 个自然日。日报通常当天晚上才上报，默认区间是最近 7 天（截止昨天）。
- **工作日**：区间内的周末和法定节假日会跳过，不产生「无记录」结论。节假日和调休来自「设置 → 工作日历」。
- **人员**：只检查「人员」页里**关注且启用**的成员。
- **项目**：只检查「项目」页里**关注且启用**、并且和日报项目名匹配上的项目。
- **刷新日报**：开始检查前会把区间内的日报重新拉一遍；拉取失败会停止检查，避免拿旧快照下结论。

## 运行过程

每个工作日 × 每个成员会产生一条结果。检查引擎会：

1. 按时间窗把 GitLab 提交归到日期；
2. 只保留属于该成员身份（GitLab 用户名/邮箱）的提交；
3. 为真正需要的提交拉取文件改动；
4. 逐条把日报内容和提交对照，给出判定；
5. 找出没有被任何日报条目引用的提交。

时间窗默认是「前一天 20:00 到次日 08:00」，可在「设置 → 判定规则」调整。相邻日期的窗口会重叠，同一个提交只归给最早命中的那天。

## 常见状态

- **没有可核对内容**：当天没有提交，或日报条目匹配不到任何仓库。分数显示「—」，不代表 0 分。
- **无法核对**：GitLab 未配置、仓库没有权限、或日报项目没有关联仓库。
- **失败**：某个人某天运行报错，会在页面顶部列出日期、人员和原因。

## 建议

- 第一次先跑 1–3 天，确认人员身份和项目关联正确，再扩大区间；
- 区间越大、关注成员越多，模型调用和 GitLab 请求越多，耗时线性增长；
- 检查结果会写入「检查历史」，可以在那里按批次回看。
